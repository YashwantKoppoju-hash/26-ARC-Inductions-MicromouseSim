A field guide to maze solving

First find the shape of the maze. Then make speed matter.

A Micromouse is two systems working as one: a planner that reasons over cells it has discovered, and a continuous controller that turns those decisions into safe velocity commands.

INPUT 3 rays / 20 HzOUTPUT Twist velocityWORLD 16 × 16 cellsGOAL central 2 × 2MAP hidden from solver
The mental model

Search is not steering.

planner ≠ controller

The loop the solver lives inside

Every scan callback is a small perception–decision–action cycle. The search layer can think in clean grid moves even though the physics layer moves continuously.

scan L / F / R→update map→choose cell→publish Twist

What this repo really assumes

The simulator knows the complete maze internally, but student_agent/solver.py does not receive it. The agent sees only three raycasts and can optionally read actual velocity from /mouse/vel.

That means the right abstraction is an online solver: maintain an estimated pose and a partial wall map, re-plan as new walls are observed, then use continuous control to reach the next cell center.

The practical Micromouse default

Assign every known cell a distance to the goal. When a new wall makes the current gradient impossible, recompute the distances and follow the next lower-valued neighbor.

DATA: distance[16][16] + wall bitmasks + visited[16][16]

How to read the picture

A real solver would not paint the whole maze in advance. The colors represent the algorithm’s internal state: cells it has visited, cells it might expand next, and the route it currently prefers.

Established solutions

Six ways to make a maze legible.

from simplest to most strategic
01

Left- or right-hand wall following

Keep one wall on a chosen side. If the next side is open, turn toward it; otherwise continue forward or turn away from the wall. It is the smallest useful baseline and a good test of the sensor-to-motor loop.

local ruleO(1) memorynot shortest
why use itAlmost no state; useful when the maze is simply connected.
where it breaksLoops and isolated wall islands can make it miss the goal or wander.
02

Depth-first search with backtracking

Treat each cell as a graph vertex. Explore one available neighbor deeply; when it leads nowhere, pop the stack and return to the last branch. DFS is complete on a finite connected maze, but the first path found can be very long.

stackvisited setcomplete
why use itDirectly mirrors exploration: discover, remember, retreat.
where it breaksNeeds deliberate reverse/turn behavior; path quality is poor without a second optimization pass.
03

Flood-fill / Bellman propagation

Store a distance value in every cell. Seed the central goal cells with zero, propagate values outward, and move toward a neighbor with a lower value. As the robot discovers walls, recompute the values on the partial map. This is the classic fit for an unknown Micromouse grid.

distance gridqueuere-planningrecommended
why use itSimple, explainable, online, and naturally handles a 2×2 goal zone.
where it breaksRequires reliable cell localization and a controller that can actually reach the selected neighbor.
04

Dijkstra’s algorithm

Expand the lowest-cost frontier using a priority queue. With equal-cost cell moves, it behaves like breadth-first search; with custom costs, it can prefer fewer turns, safer clearance, or lower energy. It is exact but more machinery than an unweighted grid needs.

priority queueweighted costsoptimal
why use itBest when “shortest” means more than fewest cells.
where it breaksOn a 16×16 unit grid, the extra abstraction adds little over flood-fill.
05

A* search

Choose frontier cells by f(n) = g(n) + h(n): known cost so far plus an estimate to the goal. Manhattan distance is admissible for four-direction unit moves, so A* can find an optimal path while expanding fewer irrelevant cells than Dijkstra.

priority queueheuristicknown-map favorite
why use itFast focused planning once the map or a useful partial map exists.
where it breaksUnknown walls still require frequent re-planning; the heuristic does not solve localization.
06

Continuous wall-centering / PID control

This is not a maze search strategy—it is the motion layer. Use the left/right ray error to keep the body centered, reduce speed near walls, and command an angular velocity while driving forward. It turns a symbolic plan such as “go north one cell” into smooth motion.

feedback controlP / PD / PIDTwist output
why use itMatches the repo’s continuous physics and prevents corner clipping.
where it breaksA controller alone cannot remember explored branches or guarantee a route to the goal.
The memory of the mouse

Small structures, strong behavior.

what the solver should remember

Discrete pose

A cell coordinate and one of four headings. Keep continuous x, y, θ estimates only for control and cell-boundary detection.

pose = {"cell": (0, 0),
        "heading": "N"}

Known walls

Encode N/E/S/W walls as bits. A dictionary is easy while learning; a fixed 16×16 array is faster and simpler once the grid is known.

# N=1, E=2, S=4, W=8
walls[(r, c)] = N | W

Visited cells

Separates “seen at least once” from “currently on the route.” It prevents endless loops and identifies places worth revisiting.

visited = [[False] * 16
           for _ in range(16)]

Distance field

Flood-fill’s compact plan: lower neighbor values point toward the goal. Recompute when newly sensed walls invalidate the gradient.

distance = [[INF] * 16
            for _ in range(16)]

Motion state

A finite-state machine stops the planner from issuing a new turn every sensor tick. It gives each action time to finish and settle.

state = "DRIVE_TO_CENTER"
target = (1, 0)
phase_start = time.monotonic()
The architecture to build

Online flood-fill, continuous execution.

a practical hybrid

The best fit is not “pick one algorithm and hope.” Keep the planner discrete and the actuator continuous. That gives you the clarity of a grid graph without pretending the robot teleports between cells.

01 / SENSE

Read rays

Filter L/F/R; classify each as wall or open using a safety margin.

02 / LOCALIZE

Update pose

Integrate actual velocity and use wall geometry to detect cell centers.

03 / MAP

Record walls

Write symmetric wall bits for the current cell and neighbors.

04 / PLAN

Flood-fill

Recompute distances; select a reachable lower-valued neighbor.

05 / ACT

Drive smoothly

Turn, center, accelerate, brake, and stop at the next reference point.

Recommended first implementation

Start with a conservative four-state controller—TURN, DRIVE, SETTLE, REPLAN—wrapped around a flood-fill map. Once it is reliable on random mazes, spend the remaining point budget on speed and sensor range, then add a second pass that replays the discovered shortest route faster.
